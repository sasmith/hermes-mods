# Repo security audit + remediation

## When to Use

The user asks to audit, review, or threat-model a repo or deployed system for security issues — and especially when they also want the findings fixed: fix sessions, history scrubbing, credential rotation, data-store purge. Per-repo architectural facts live in that repo's own skill; this one carries the cross-repo procedure.

## Procedure

0. **Re-audit? Start from the prior findings.** Recall the earlier audit (memory + its report file). For every prior finding, record FIXED (file:line on the audited commit), STILL OPEN, or REGRESSED. Check that the earlier fix branches actually landed by searching main for their commit subjects or changes, not only `merge-base --is-ancestor`: squash or rebase landings break ancestry, and branches that were never merged look the same until you check. Report "fix branch never merged" as a finding.
1. **Orient on fresh clones, not working checkouts.** Clone each repo shallow (`--depth 100`) into a scratch dir. Working checkouts are often dirty/stale on side branches; history greps against them hit unrelated worktrees. Record the audited commit in the report so findings are attributable.
2. **Dispatch one audit subagent per area, not only per repo.** When the user says "and the <agent> setup", the hosts are in scope too: one subagent each for the edge/Worker, the hub/authority layer, prompt-injection paths into agents with tools, every host (listeners, firewall, secret file permissions, sshd, tailnet peers, agent config such as approvals, toolsets, MCP servers, browser profile, plugin sources), and clients/devices/update supply chain. Write ONE shared brief file and point every subagent at it: read-only, never print secret values (report path, perms and an 8-char sha prefix), write the findings file incrementally (subagents are killed around 11 minutes), give each prior finding's status, and end with "Verified solid" and "Not checked" lists. Each needs a threat model enumerating the actor positions (anonymous internet, LAN peer, stolen credential, supply chain, prompt-injection→agent-with-tools) and demand file:line-grounded findings with concrete attack scenarios — 5 grounded findings beat 20 speculative ones, and "verify the signed-command implementation actually works" is as valuable as finding holes.
3. **Report shape:** lead with the kill chain (the cheapest path from the least-trusted input to the most dangerous action), then ONE table of every finding (# · severity · finding with file:line · remedy), then "fixed since last audit", "verified solid" and "not checked". Mark the items you re-verified yourself. End with the few 10-minute stopgaps and an offer to fan out fix cards.
4. **Live-verify the top findings yourself before acting on them.** Probe prod read-only first (does the leaked credential still authenticate? does the unauth request actually return 200?). An audit claim of "rotated" or "dead key" is a hypothesis until tested — AWS STS `get-caller-identity` with the candidate creds, curl the endpoint with and without auth. Never print secret values in transcripts or terminal output; pipe them between processes.
5. **Save the results in the audited repo** (when it's private): `docs/security/<date>-audit/` with the report, the per-area findings and the brief, plus a `docs/security/README.md` index row. Run gitleaks on each file you add (scan per file; a directory scan picks up unrelated hits), then make a docs-only push.
6. **Remediating autonomous agent loops (self-fix, auto-merge, auto-deploy):** don't propose "add a human to every merge" or "take the agent's tools away" as the default; this user wants the system to keep repairing itself with minimal intervention. Move the boundary from the agent to a small trusted pipeline the agent can't edit:
   - a sandboxed author (its own OS user and a token that can only push branches and open PRs);
   - provenance tiers on what it works on (owner / household / unverified / system), set from authenticated context and never from model arguments;
   - an independent no-tools reviewer on every PR;
   - deterministic green / amber / red tiers from a policy file read from the BASE commit, so a PR can't relax its own rules. Red covers auth, roles, CI, signing, updates and the gate itself, and needs the owner's approval on the exact head SHA;
   - canary deploy with auto-revert;
   - signing keys out of the agent's reach.
   Measure the human-tap cost from the merge ledger (share of recent merges touching red paths) and put that number in the plan. Prefer holds and one-tap phone confirmations over refusals or tool removal. Removing tools or flipping approval modes is a separate step the user must agree to, and they may defer it: then build the gate, and state the remaining gap plainly (e.g. an agent still holding the merge token can bypass the gate).
7. **Group findings into non-overlapping work areas** and dispatch one fix session per group in an isolated worktree (see subagent-driven-development for the parallel-worktree pattern): auth core, web layer, upload/ingest pipeline, availability, secrets/history, CI pins. Name a scope guard in every brief — the exact functions/files sibling sessions own. All sessions branch-only; the controller integrates. For a live home/production system where the user has standing ship approval, use one Kanban card per finding instead, plus a shared-rules file every card reads first: a regression test that fails on main before the fix; list every legitimate caller (grep plus a live check) before tightening auth or exposure; ship as soon as tests pass; prove live that the attack is refused AND the legitimate path still works. Give a design-changing finding (e.g. who may command by voice) a design phase that blocks for the user's go, grounded in measured data, with a failure budget and a shadow mode before enforcement.
8. **Integrate sequentially, resolve conflicts once, then verify**: run the combined security-test battery plus core suites on the merged tree; reproduce any remaining failures on pristine main before accepting them as pre-existing. Fix fixtures broken by the merge itself (a security fix that makes auth mandatory breaks every test fixture that boots without credentials — update fixtures to the new contract, don't weaken the fix).
9. **Rotate in dependency order**: password/tokens first (generate in-process, never on disk in the repo), then sync every downstream copy (Worker store, Fly secrets, GitHub secrets, broker scopes), then purge git history (filter-repo on a sacrificial clone, force-push, delete stale leak-carrying branches), then purge data stores (D1 rows, FTS, R2 objects, snapshots). Verify each rotation live: old credential → 401, new → 200, anonymous → 401.
10. **Store rotated credentials in the token broker** as `user/<name>` auto scopes (see token-broker skill) so future sessions can vend them — not in repo files or chat.

## Pitfalls

- Grep history for the leaked string AFTER the fix sessions land, not just the audit — a fix session may re-introduce it as a test fixture value ("wrong password" literals). Scrub the fix first, then rewrite history, or the rewrite re-imports the leak.
- Test suites that boot servers without credentials fail wholesale once auth becomes fail-closed; check whether the module caches env at import (`AUTH = os.environ.get(...)` at module level) — fixtures must set the module attribute or boot a subprocess with env, and raw-socket probes must carry the auth header.
- Data-store purge must follow the data's actual replication paths, not the obvious one: an indexed note lands in the FTS index and in hashed R2 objects and in daily/monthly snapshots with different key schemes — compute the hash keys from the ingest code, and remember monthly snapshot copies have no lifecycle rule.
- Don't trust a commit message claiming rotation; test the old credential against the live service.
- A history rewrite of main doesn't remove the leak from GitHub: the old commit stays fetchable while any other branch, tag or fork still reaches it. Check `gh api repos/<o>/<r>/commits/<old-sha>`. If it still resolves, delete the stale branches and ask GitHub support to GC.
- Minting a credential that only exists behind a web UI (a fine-grained PAT, an OAuth app): this user prefers you do it. Drive his logged-in everyday Chrome through the chrome-devtools MCP tools (`new_page`, `take_snapshot` with `filePath`, `click`, `fill`). Read the one-time token value with `evaluate_script` and its `filePath` argument, so the value lands in a 0600 scratch file and never in the transcript. Check its scope by API (allowed repo 200, other repo 404) before storing it. Store it in the target store and the broker from a script, then delete the scratch file. Default to the narrowest repo and permission set, and ask about expiry: he chose no expiration for these. Only when he wants to do it himself: open the URL and launch a `run_in_user_terminal` script that uses the CLI's interactive prompt, never a `--value` flag.
- Capture and redact the output of every call that sends a secret (`github_pat_…`, `gho_…`, `sk-…`). Validation errors echo the request body: a broker 422 printed two new tokens into the transcript and forced an immediate rotation. GitHub's "Regenerate token" keeps the token's scopes, so rotating is cheap: regenerate, re-store, and confirm the old values return 401.
- Split a shared credential without downtime. Create the NEW secret slot first, ship the code that reads it, then overwrite the OLD slot with the narrower value. Overwriting first breaks the live service, because deployed code still reads the old slot for the removed duties. Redeploy after the swap so cached isolates pick up the new value.
- Before revoking "the old token", identify what it is (prefix and `/user` response headers, never the value). A `gho_` value is a GitHub CLI OAuth login, not a PAT. It can only be killed by revoking the whole GitHub CLI app, which logs out every machine's `gh`. Ask first, and don't propose narrowing the user's own hosts: he wants his machines to keep full access. Narrow only credentials that leave them (edge Workers, third-party services).
- Before re-tightening a security setting that drifted (e.g. agent approvals turned off), find out why it drifted: config backups and mtimes, session logs, the job that failed just before. These approvals were turned off because unattended jobs blocked on prompts nobody could answer. So the fix for unattended runs is `deny`, not a prompt, or the stall returns.
- For a sudo step on the user's hosts, put the commands in one script that tees to a log, launch it for him, and read the log for the result. If `run_in_user_terminal` can't open a window (an osascript timeout), launch a `.command` file with `open -a Terminal <file>.command` instead, which needs no AppleScript. Never ask him to paste commands himself.
- Force-push rewrites fire auto-deploy; verify prod health (and the security fix itself) right after the push, not just the git state.
- This user's remediation preferences: (1) don't disable risky tools or capabilities; log and count their use (a metadata-only risk ledger plus stats), then propose reductions one at a time from the numbers; (2) no SSH key passphrases. SSH hygiene means per-host `IdentityFile` + `IdentitiesOnly`, no blanket `ForwardAgent`, and commenting out (not deleting) unused `authorized_keys`; (3) never burn eFuses or other irreversible hardware settings without his explicit go. Write these into the shared-rules file every fix card reads.
- Never claim "history was rewritten" or "the leak is gone from history" from a shallow or grafted clone: the oldest commit you see is just the depth cutoff. Run `git merge-base --is-ancestor <leak-sha> origin/main` on a full clone. If main still contains it and the credential is confirmed dead (IAM deleted, STS rejects it, no CloudTrail use), "no rewrite" is a legitimate decision for a private repo. A rewrite breaks every worktree, open PR, merge queue and SHA-pinned deploy.
- Re-check where CI actually runs (`runs-on` across workflows) at every audit. To dodge Actions billing, CI can move silently to self-hosted runners on shared multi-user machines, and then any job that loads signing keys exposes them to everyone with shell on that box. Pin secret-bearing jobs to an owner-only host or to hosted runners, clean the workspace after each job, and check runner disk space (a full disk fails every job).
